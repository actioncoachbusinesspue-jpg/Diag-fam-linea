2. OBJETIVO DE LA VERSIÓN EN LÍNEA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Construir el segundo camino del proyecto:

1. Cualquier persona con la liga pública puede abrir la plataforma.
2. La demostración ficticia puede consultarse sin contraseña.
3. Solo el equipo BVM puede entrar a Administración BVM.
4. Administración BVM debe requerir usuario y contraseña reales, validados en el servidor.
5. BVM puede crear y administrar varias familias o empresas.
6. Al crear una familia, el sistema genera una liga única y una clave de acceso.
7. Los participantes pueden responder desde teléfonos o computadoras diferentes.
8. Las respuestas se guardan centralmente en MySQL/MariaDB.
9. BVM puede consultar el avance en tiempo real.
10. Los participantes no pueden ver resultados ni Administración BVM.
11. El reporte ejecutivo se genera con las respuestas finalizadas.
12. El reporte conserva exactamente su metodología, diseño y estructura de 12 páginas.
13. La Familia Horizonte permanece como demostración ficticia y aislada.
14. La solución debe poder subirse a Hostinger sin procesos complejos de servidor.

El flujo final debe ser:

BVM inicia sesión
→ crea familia
→ define participantes esperados y vigencia
→ el sistema genera liga y clave
→ BVM comparte la invitación
→ cada participante accede desde su equipo
→ se registra y obtiene un código personal de continuidad
→ responde con guardado automático
→ finaliza y queda bloqueado
→ BVM ve avances agregados
→ BVM genera la radiografía y el reporte.

3. TECNOLOGÍA RECOMENDADA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Utiliza una arquitectura compatible con hosting compartido:

- PHP 8.2 o una versión estable disponible en el hosting;
- MySQL o MariaDB;
- PDO;
- HTML semántico;
- CSS propio;
- JavaScript vanilla modular;
- sesiones PHP;
- HTTPS;
- Apache/.htaccess cuando esté disponible.

No utilices Node.js como requisito de producción.

Node.js y Playwright pueden utilizarse localmente para pruebas, pero la aplicación publicada debe funcionar con PHP y MySQL/MariaDB.

Evita dependencias remotas y CDNs.

La aplicación debe seguir funcionando si el navegador bloquea recursos de terceros, porque no debe requerirlos.

No uses frameworks pesados salvo que exista una justificación técnica contundente. Prioriza una solución sencilla de instalar, auditar y mantener.

5. EXPERIENCIA PÚBLICA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

La página pública debe mostrar tres caminos:

A. RESPONDER EL DIAGNÓSTICO
Para personas invitadas por una familia.

B. CONOCER LA RADIOGRAFÍA BVM
Demostración con Familia Horizonte, completamente ficticia.

C. ACCESO BVM
Uso exclusivo del equipo autorizado de BVM.

Jerarquía recomendada:

- acción principal: Responder diagnóstico;
- demostración claramente visible, con explicación del beneficio y duración;
- Acceso BVM visible pero sobrio, acompañado de un icono de candado;
- no presentar Administración BVM como una opción disponible para participantes.

El botón de demostración debe aparecer:

- en la página inicial;
- en el estado inicial cuando no se ha ingresado a una familia;
- dentro de la ayuda;
- con el texto “Iniciar demostración guiada”;
- con una explicación breve de qué permite conocer;
- con duración estimada;
- con opción de minimizar o salir;
- sin competir con la acción principal cuando existe una invitación real.

La experiencia debe sentirse:

- premium;
- sobria;
- fluida;
- propia de alta dirección;
- clara;
- no saturada;
- no parecida a un SaaS genérico.

Debe mantener:

- navegación consistente;
- estado activo visible;
- contexto de ubicación;
- breadcrumbs cuando ayuden;
- regreso sencillo;
- ayuda permanente;
- foco y teclado accesibles;
- experiencia móvil completa;
- transiciones discretas;
- continuidad sin perder datos.

6. ACCESO BVM SEGURO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Implementa autenticación real del lado del servidor.

No guardar usuario o contraseña dentro de JavaScript, HTML, CSS o localStorage.

Requisitos:

- tabla de usuarios;
- password_hash para almacenar contraseñas;
- password_verify para validar;
- sesiones PHP;
- regenerar ID de sesión al iniciar sesión;
- cookie HttpOnly;
- cookie Secure cuando existe HTTPS;
- SameSite=Strict o Lax con justificación;
- cierre de sesión;
- expiración por inactividad;
- protección CSRF;
- límite de intentos;
- bloqueo temporal tras intentos repetidos;
- mensajes genéricos de error;
- consultas preparadas PDO;
- validación y escape de salidas;
- no revelar si un usuario existe;
- no registrar contraseñas;
- no registrar respuestas individuales en logs.

Crear un asistente de instalación inicial seguro:

- solo funciona cuando no existe ningún usuario;
- exige un token de instalación ubicado en configuración privada;
- crea el primer administrador;
- se deshabilita automáticamente al completar la instalación;
- no deja credenciales predeterminadas;
- no utiliza admin/admin ni contraseñas fijas.

Preparar la arquitectura para roles:

- administrador;
- consultor.

En el MVP puede existir un solo administrador, pero la base de datos debe permitir agregar consultores posteriormente.

Un consultor nunca debe acceder a familias que no le fueron asignadas cuando se habiliten varios usuarios.

7. ALTA Y ADMINISTRACIÓN DE FAMILIAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Administración BVM debe permitir:

1. Crear familia o empresa.
2. Editar el nombre.
3. Definir número esperado de participantes.
4. Definir fecha de apertura.
5. Definir fecha de cierre.
6. Cambiar estado:
   - borrador;
   - abierta;
   - cerrada;
   - archivada.
7. Copiar la liga de invitación.
8. Generar o regenerar clave de acceso.
9. Consultar avance:
   - registrados;
   - en proceso;
   - finalizados;
   - porcentaje;
   - última actividad.
10. Abrir resultados.
11. Generar reporte.
12. Exportar respaldo.
13. Archivar.
14. Eliminar de forma definitiva únicamente con doble confirmación.
15. Reabrir una participación finalizada únicamente con autorización expresa y registro de auditoría.

Al crear una familia, genera:

- identificador interno;
- slug público aleatorio no predecible;
- liga pública;
- clave de familia aleatoria;
- fecha de creación;
- estado inicial;
- usuario BVM responsable.

La clave de familia:

- debe generarse de manera criptográficamente segura;
- debe mostrarse al administrador para copiarla;
- debe almacenarse como hash;
- si se pierde, se regenera;
- nunca debe enviarse al navegador público desde la API;
- no debe utilizarse como contraseña administrativa.

Ejemplo conceptual:

Liga:
https://dominio.com/diagnostico-bvm-online/participar.php?f=RANDOM_SLUG

Clave:
ROBLES-8K4P

La liga identifica la familia.

La clave autoriza el acceso para responder.

Ninguna de las dos permite entrar a Administración BVM.

8. EXPERIENCIA DEL PARTICIPANTE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Flujo:

1. Abrir liga de familia.
2. Ver una bienvenida sin mostrar información sensible innecesaria.
3. Ingresar clave de familia.
4. Leer aviso de privacidad y consentimiento.
5. Registrar:
   - nombre;
   - generación;
   - tipo de participación;
   - rol patrimonial.
6. El sistema genera un código personal de continuidad.
7. Mostrar el código una vez y permitir copiarlo.
8. Comenzar cuestionario.
9. Guardar cada respuesta automáticamente.
10. Mostrar estado:
    - Guardando…
    - Guardado.
    - Sin conexión; reintentando.
11. Permitir salir y continuar posteriormente.
12. Permitir continuar desde otro dispositivo usando:
    - liga de familia;
    - clave de familia;
    - código personal.
13. Revisar respuestas.
14. Responder las dos preguntas externas.
15. Finalizar.
16. Bloquear modificaciones.
17. Mostrar confirmación.

El código personal:

- debe ser aleatorio;
- no debe derivarse del nombre;
- debe guardarse como hash;
- debe poder regenerarse desde Administración BVM;
- no debe permitir ver respuestas de otra persona;
- no debe permitir ver resultados familiares.

Evitar duplicados razonables:

- normalizar espacios;
- comparación insensible a mayúsculas;
- advertir si ya existe un nombre igual;
- permitir nombres iguales únicamente con confirmación administrativa o identificador distinto.

No usar correo electrónico como requisito en el MVP.

No pedir datos que no son necesarios.

9. GUARDADO, CONCURRENCIA Y CONTINUIDAD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Sustituir localStorage como fuente principal de datos reales.

La base de datos debe ser la fuente de verdad.

localStorage puede conservar únicamente:

- preferencia de interfaz;
- código o token de continuidad cifrado o protegido de forma razonable;
- última ruta;
- estado temporal no sensible;
- onboarding visto.

No guardar el conjunto completo de respuestas reales en localStorage.

El guardado automático debe:

- guardar una respuesta por operación;
- validar que el valor esté entre 1 y 5;
- usar transacciones;
- impedir cambios después de finalizar;
- manejar pérdida temporal de conexión;
- reintentar sin duplicar;
- informar al usuario;
- conservar orden e índice actual;
- registrar updated_at;
- usar un número de revisión para detectar ediciones simultáneas.

Si dos dispositivos intentan editar la misma participación:

- detectar conflicto;
- no sobrescribir silenciosamente;
- conservar la versión más reciente confirmada;
- mostrar un mensaje comprensible;
- permitir recargar.

11. PRIVACIDAD Y CONTROL DE ACCESO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- entrar a Administración BVM;
- listar familias;
- conocer otras familias;
- acceder mediante cambio de ID;
- ver resultados;
- ver respuestas de otros;
- consultar participantes;

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Primero:

- inspecciona el HTML de referencia;
- crea un inventario de módulos;
- identifica todas las funciones de StorageAdapter;
- identifica todos los motores de cálculo;
- identifica rutas del participante, demo y admin;
- identifica respaldo, impresión y onboarding;
- crea un mapa de migración.

Después implementa.

No respondas solo con recomendaciones.

No entregues maquetas estáticas.

No simules una base de datos con localStorage.

No declares seguridad si la contraseña está en el frontend.

No modifiques el archivo estable.

No mezcles versión local y versión en línea.

No publiques credenciales.

No inventes metodología.

No elimines funciones para terminar más rápido.

No declares “listo” sin pruebas reales.

El objetivo es una versión piloto en línea profesional, segura, centralizada y defendible, sin perder el trabajo ya validado.
